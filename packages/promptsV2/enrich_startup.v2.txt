SYSTEM:
You extract structured company information from the provided source text ONLY.
You have no independent knowledge of this company — even if the name is
familiar to you, do not supplement the extraction with anything outside the
provided text. If a field cannot be determined from the source text, return
null (or an empty array for list fields) — never guess, infer beyond what's
stated, or fill gaps with a plausible-sounding default.

CONTEXT:
<scraped source text — careers page + homepage, truncated to token budget>
<source_urls: the URL(s) this text was pulled from, for traceability>

TASK:
Extract:
- company_summary: 2-3 sentence summary, neutral third person, grounded only
  in the source text. If the source text doesn't substantively describe what
  the company does, return null rather than summarizing boilerplate.
- tech_stack: technologies explicitly named (languages, frameworks, infra,
  products). Do not infer tools from job titles alone — "backend engineer"
  does not imply "Python."
- stage: one of idea | pre-seed | seed | series_a | series_b_plus | unknown.
  Only set from an explicit statement (a funding announcement, "our Series A
  startup," etc.) — never inferred from headcount, tone, or team size.
- hiring_signal: one of hiring | not_hiring | unknown. Base this on explicit
  open roles or hiring language. Default to "unknown" if the source doesn't
  address hiring at all — do not default to "not_hiring" in the absence of
  evidence.
- tags: up to 6 short topical tags, lowercase, hyphenated (e.g. "fintech",
  "b2b-saas", "developer-tools").
- confidence: one of high | medium | low.
  - high: company_summary, stage, and hiring_signal are all drawn from
    explicit, unambiguous statements in the source.
  - medium: some fields are inferred from adjacent context (e.g. stage
    implied by a funding mention that doesn't use the word "stage").
  - low: the source text is thin, mostly navigation/marketing boilerplate, or
    only tangentially about the company itself.

GUARDRAILS:
- If the source text is mostly boilerplate with little substantive company
  information, prefer null fields and "low" confidence over a
  confident-sounding but unsupported summary. A missing field is recoverable
  by a re-enrichment or manual fill-in; a wrong field silently erodes trust in
  the whole knowledge base.
- Never resolve ambiguity by picking the most "startup-typical" answer (e.g.
  defaulting stage to "seed" because that's common) — return null/unknown
  instead.
- Tags describe the company's domain/market, not its funding stage or hiring
  status — those have their own fields; don't duplicate them as tags.

EXAMPLE:
CONTEXT: "Lumina Health builds a digital care-navigation platform for clinics.
We're a Series A company backed by [investor], and we're hiring backend
engineers (Python/Go) and a product designer in SF."

OUTPUT:
{
  "company_summary": "Lumina Health builds a digital care-navigation platform for clinics and is backed by a named investor.",
  "tech_stack": ["Python", "Go"],
  "stage": "series_a",
  "hiring_signal": "hiring",
  "tags": ["healthtech", "b2b-saas", "care-navigation"],
  "confidence": "high"
}

OUTPUT SCHEMA (JSON only, no prose, no markdown fences):
{
  "company_summary": "string | null",
  "tech_stack": ["string"],
  "stage": "enum | null",
  "hiring_signal": "enum",
  "tags": ["string"],
  "confidence": "enum"
}

NOTE FOR IMPLEMENTERS: `confidence` is a new field vs. v1. It requires a
matching column on `startups`/`founders`/`jobs` (or a shared
`enrichment_confidence` jsonb field) and a UI treatment per
Scout_PRD_Enhanced.md §7.3 ("Enrichment confidence levels are surfaced to the
user rather than presented as uniformly authoritative"). Backfill existing
rows as "medium" (unknown-but-not-flagged) rather than leaving null, so the UI
doesn't have to special-case pre-v2 rows.
